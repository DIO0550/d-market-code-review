# 防御的コード・フォールバック コードレビュープロンプト

目的: 仕様が要求していない「念のため」のフォールバックや防御的コードを検出し、削除または仕様化を促す。不要な分岐はコードの How を濁らせ、テストされない死んだ経路を増やし、読み手が「この失敗は実際に起こるのか」を判断できなくする。

## レビューポリシー

- エラー処理は仕様が要求する場所(システム境界、エントリポイント、ハンドラ)にだけ書く。それ以外の場所では失敗をそのまま伝播させる。
- 仕様が要求していない「念のため」のフォールバック・防御的コードは原則禁止。
- フォールバックが本当に仕様(合意済みの劣化提供)なら、次の3点セットを必ず揃える:
  1. なぜ許容するのかを書いたコメント(Why と出典番号)
  2. フォールバック発生に気づける観測手段(ログ、メトリクス)
  3. その挙動を固定するテスト(What)

## チェックリスト

- [ ] 起こりえないエラーへの try-catch がないか
- [ ] 呼び出し元が処理すべき例外をその場で catch して null/既定値に変換していないか(例外の握りつぶし)
- [ ] 型やバリデーションで保証済みの値への「とりあえず」の null チェック・既定値(`?? ""` 等)がないか
- [ ] 「動かすこと」を優先してエラーを catch し既定値で続行する、失敗時に黙って別実装へ切り替える、といったごまかしがないか
- [ ] 仕様としてのフォールバックに3点セット(コメント+出典 / 観測手段 / テスト)が揃っているか
- [ ] エラー処理がシステム境界に集約されているか(途中の層で散発的に catch していないか)

## 禁止/削除対象(代表例)

### 不要な try-catch

```ts
function getUser(id: string): User | null {
  try {
    return repo.findById(id);
  } catch {
    return null;
  }
}
```

`findById` は見つからなければ null を返す設計で、ここで捕まえるべき例外はない。「念のため」の catch は、実際に何かが投げられたとき(DB接続断など)に本来伝播すべき失敗まで null に変換し、呼び出し元では「ユーザーがいない」と区別できなくなる。

### とりあえずの既定値

```ts
// 型定義上 profile は必須フィールド
const name = user.profile?.name ?? "";
```

型で保証済みの値への「とりあえず」の防御。もし本当に欠けるならデータ不整合であり、空文字でごまかさず失敗させるべき。この種の分岐はテストされない死んだ経路として残り続ける。

### 動かすための既定値フォールバック

```ts
let config: Config;
try {
  config = await loadConfig(path);
} catch {
  config = DEFAULT_CONFIG;
}
```

仕様で合意されていないのに「動くこと」を優先した例。設定ファイルの破損やパスミスが無言のまま既定値動作になる。

## 推奨パターン

### 失敗をそのまま伝播させる

```ts
function getUser(id: string): User | null {
  return repo.findById(id);
}
```

エラー処理を書かないことが正解の場合も多い。想定外の失敗はシステム境界(エントリポイント、リクエストハンドラ)まで伝播させ、そこで一元的に処理する。

### 仕様としてのフォールバック(3点セット)

```ts
try {
  return await recommendItems(userId, limit);
} catch (err) {
  // 推薦APIの障害時は人気順で代替する(SPEC-044)。
  // 推薦は補助機能であり、一覧ごと落とすより劣化提供が望ましいと合意済み。
  // 障害に気づけるよう warn ログとメトリクスを必ず残す。
  logger.warn("recommendation fallback", { err });
  metrics.increment("recommend.fallback");
  return popularItems(limit);
}
```

Why(なぜ許容するか)と出典番号のコメント、観測手段(ログ・メトリクス)が揃っている。このフォールバック挙動自体をテストで固定する。

## レビュー出力フォーマット(最小)

- Remove: <場所> — 不要な防御の種類(握りつぶし/型保証済み値への既定値/黙示のフォールバック)と、削除して伝播させる提案
- Promote-To-Spec: <場所> — フォールバックが妥当と思われる場合、仕様化+3点セット(コメント/観測/テスト)の提案
- Add-Observability: <場所> — 仕様フォールバックに不足している観測手段・テスト
- Relocate: <場所> — エラー処理をシステム境界へ移動する提案

## 重要度

- 🔴 Blocking: 例外の握りつぶし(catch して null/既定値で続行し、実際の失敗を隠すもの)、失敗時に黙って別実装へ切り替えるフォールバック
- 🟡 Should Fix: 型・バリデーションで保証済みの値への防御、起こりえないエラーへの try-catch、仕様フォールバックの3点セット不足(コメント・観測手段・テストのいずれか欠落)
- 🟢 Nice to Have: エラー処理のシステム境界への集約、フォールバックコメントへの出典番号追加

この方針: 「エラー処理は仕様が要求する場所にだけ。それ以外は伝播」。フォールバックを書くなら仕様として合意し、コメント・観測・テストの3点で支える。
